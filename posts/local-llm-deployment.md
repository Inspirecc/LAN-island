## 一、一个需要算账的选型

调用大模型 API 是这个时代最简单的技术集成之一:申请 key、发个 HTTP 请求、拿到结果。相比之下,本地部署要准备 GPU 机器、下载几十 GB 的模型权重、搞定推理框架和环境依赖——门槛高出几个数量级。

那为什么还有人选择本地部署?

因为**这是一道需要算账的题**,而账单不只包括"每次调用多少钱"。

## 二、三个核心优势

### 1. 长期使用成本低

云端 API 按 token 计费,每次调用都是真金白银。本地部署则是**一次性投入 + 边际成本近乎为零**。

| | 云端 API | 本地部署 |
|---|---|---|
| 计费方式 | 按 token 计费,用多少付多少 | 一次性硬件投入 |
| 高频调用 | 成本线性增长 | 边际成本≈电费 |
| 低频调用 | 成本极低 | 硬件闲置,不划算 |
| 成本拐点 | — | **调用量超过某个阈值后,本地更便宜** |

**关键判断依据是调用量**:偶尔用几次,云端 API 明显更划算;但如果是持续高频的批处理任务(比如每天处理几十万条数据),云端账单会迅速超过一台机器的价格。

不过要注意,本地部署的账要算全:

| 成本项 | 说明 |
|---|---|
| 硬件 | GPU 显卡 / 显存,这是大头 |
| 电费 | 推理时 GPU 功耗不低,长期运行要算进去 |
| 运维人力 | 环境维护、模型更新、故障处理 |
| **机会成本** | 团队花在部署上的时间,本可以用于业务开发 |

小模型能跑在消费级显卡上,大模型的硬件成本则相当可观。**"省下的 API 费用"能否覆盖这些成本,取决于调用量和模型规模。**

### 2. 数据不出内网

这是很多场景下的**决定性因素**。

云端 API 意味着:你的数据要**离开自己的网络**,发到第三方服务器上。对于以下场景,这可能是不可接受的:

| 场景 | 为什么敏感 |
|---|---|
| 企业内部文档问答 | 涉及商业机密、未公开的产品规划 |
| 医疗 / 病历处理 | 受法规约束的个人健康信息 |
| 金融 / 客户资料 | 合规要求,数据不得出境或外传 |
| 法律文书分析 | 客户保密义务 |
| 政府 / 军工 | 涉密信息,物理隔离要求 |

**本地部署的数据流向完全不同:**

```
云端 API:  你的服务器 ──→ 公网 ──→ 厂商服务器(数据落地)
本地部署:  你的服务器 ──→ 内网 ──→ 本地 GPU 机器(数据不出网)
```

**物理隔离**意味着数据在传输和存储上都完全自主可控——不是靠"相信厂商的隐私政策",而是**从架构上就不可能外泄**。

> 这一点在合规审查时往往不是"加分项",而是"准入条件"。数据不出内网是硬性要求时,云端方案直接出局,成本比较也就没有意义了。

### 3. 完全自主可控

| 维度 | 云端 API | 本地部署 |
|---|---|---|
| **模型版本** | 厂商随时升级/下线,你的 prompt 可能失效 | 锁定版本,行为稳定 |
| **服务稳定性** | 依赖厂商可用性,可能限流/宕机 | 自己掌控 |
| **能力定制** | 只能用厂商提供的能力 | 可微调、可改推理参数、可加自定义逻辑 |
| **供应商风险** | 涨价、停服、条款变更 | 无 |

**模型版本漂移是个容易被低估的问题**:厂商升级模型后,同样的 prompt 可能给出不同质量的回答,而你的系统已经针对旧版本调优过了。本地部署可以锁定版本,想升级时再升——**升级是主动决策,不是被动接受**。

## 三、本地部署的代价

说完优势,必须说清楚代价,否则就不是技术判断而是推销了:

| 代价 | 说明 |
|---|---|
| **门槛高** | 需要 GPU 环境、推理框架(CUDA、vLLM、Ollama 等)、模型权重管理 |
| **效果差距** | 开源模型在通用能力上通常弱于头部闭源模型,复杂推理差距更明显 |
| **硬件投入** | 大模型需要大显存,消费级显卡往往只能跑量化后的小模型 |
| **并发能力有限** | 单机吞吐远不及厂商集群,高并发场景需要自己做负载均衡 |
| **维护成本** | 模型更新、显存优化、故障排查都要自己来 |
| **没有兜底** | 云端服务出问题可以找厂商,本地的只能自己解决 |

### 硬件与模型规模的对应关系

粗略的经验判断:

| 模型规模 | 量化后显存需求 | 典型硬件 |
|---|---|---|
| 1.5B ~ 3B | 2 ~ 4 GB | 消费级显卡、甚至 CPU |
| 7B ~ 8B | 5 ~ 8 GB | 主流消费级显卡 |
| 14B | 10 ~ 16 GB | 高端消费级显卡 |
| 32B | 20 ~ 24 GB | 专业卡 / 多卡 |
| 70B+ | 40 GB+ | 多卡 / 服务器级 |

**量化**(把权重从 FP16 压到 INT8 / INT4)能大幅降低显存需求,代价是效果会有一定损失。这是本地部署最常用的折中手段。

## 四、混合方案:按敏感度分流

实践中,最合理的往往不是"全云端"或"全本地",而是**按数据敏感度分流**:

```
                    ┌─ 敏感数据 / 高频批处理 ──→ 本地模型
用户请求 ──→ 路由判断 ─┤
                    └─ 一般问答 / 复杂推理 ────→ 云端 API
```

| 请求类型 | 走哪边 | 理由 |
|---|---|---|
| 含内部文档、客户信息 | 本地 | 合规要求 |
| 大批量文本分类/抽取 | 本地 | 成本优势明显 |
| 需要强推理能力的复杂任务 | 云端 | 效果优先 |
| 低频、非敏感的一般问答 | 云端 | 成本低、免运维 |

**这样既守住了数据红线,又在需要模型能力的地方用上了最强的模型。**

分流的关键是**路由判断的准确性**——一旦把敏感数据误判到云端,合规防线就破了。所以路由规则通常要保守一些:**不确定就本地**。

## 五、选型决策清单

按顺序问自己这几个问题:

| # | 问题 | 如果答案是"是" |
|---|---|---|
| 1 | 数据是否涉及合规红线(个人隐私/商业机密/涉密)? | **必须本地**,成本比较到此结束 |
| 2 | 调用量是否足够大(日均百万 token 以上)? | 本地更划算,可以算成本拐点 |
| 3 | 是否需要锁定模型版本、避免行为漂移? | 本地优先 |
| 4 | 团队有没有 GPU 运维能力? | 没有则优先云端,或用托管推理服务 |
| 5 | 对模型能力要求是否极高(复杂推理/长链任务)? | 云端优先,或本地+云端混合 |
| 6 | 是否需要微调定制? | 本地(云端微调成本高、数据也要外传) |

## 小结

- 本地部署的三大优势:**长期成本低**、**数据不出内网**、**完全自主可控**
- **数据合规往往是决定性因素**——是准入条件,不是加分项
- 成本账要算全:硬件 + 电费 + 运维人力 + 机会成本,不只是"省下的 API 费用"
- 本地部署的代价很实在:**门槛高**、**效果差距**、**并发有限**、**维护全自理**
- **模型版本漂移**容易被低估:本地可锁定版本,让升级变成主动决策
- 常见最优解是**混合方案**:按数据敏感度分流,敏感和批量走本地,复杂推理走云端
- 分流规则要保守:**不确定就本地**

"要不要本地部署"没有标准答案,但判断的框架是清晰的:**先看合规红线,再算调用量,最后看团队能力**。按这个顺序问下来,答案通常就自己浮出来了。
