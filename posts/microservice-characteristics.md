## 一、先明确一件事:微服务不是技术升级

很多讨论把微服务描述成"比单体更先进的架构",这是误解。

**微服务解决的核心问题是组织问题,不是技术问题。**

一个 5 人团队做的小系统,拆成 20 个微服务只会让所有人都痛苦。而一个 200 人团队维护的单体应用,几乎必然演变成"改一行代码要全量发布、发一次版要协调八个组"的困局。

判断要不要微服务,先看两个指标:

| 指标 | 单体更合适 | 微服务更合适 |
|---|---|---|
| 团队规模 | < 10 人 | 多个团队并行开发 |
| 业务复杂度 | 单一业务域 | 多个相对独立的业务域 |
| 发布频率 | 每周/每月 | 每天多次 |
| 并发量级 | 单机可承载 | 需要按模块独立扩容 |

## 二、微服务的七个特点

### 1. 服务拆分,单一职责

把一个庞大单体按**业务域**拆成多个独立小服务,每个服务只负责一块业务——用户服务、订单服务、商品服务。

关键是"按业务域拆",不是"按技术层拆"。拆成"Controller 服务""Service 服务""DAO 服务"是典型的错误拆法——这只会把一次本地方法调用变成三次网络调用,没有任何收益。

**判断拆分边界的原则**:高内聚、低耦合。一个完整的业务能力(比如"下单")应该落在一个服务内,而不是跨越五个服务。

### 2. 独立部署、独立演进

每个微服务可以单独打包、单独上线、单独回滚。

修改订单服务,不需要把整个系统重新发布,也不影响其他服务。这是微服务最直接的收益——**发布风险的隔离**。

对比一下:

| | 单体 | 微服务 |
|---|---|---|
| 改一个功能 | 全量重新部署 | 只部署该服务 |
| 发布失败 | 整个系统回滚 | 只回滚该服务 |
| 发布频率 | 受整体牵制 | 各服务独立 |

### 3. 松耦合,通过网络通信

服务之间不直接调用内部方法,而是通过 HTTP / RPC 交互。

这条"通过接口而非内部实现交互"的约束带来一个副作用:**它强迫团队把接口定义清楚**。单体里那种"直接 import 别人的类、改别人的方法签名"的随意耦合,在微服务里做不到。

代价也很明显:**本地方法调用变成了网络调用**。多出来的问题包括超时、重试、序列化开销、网络抖动、部分失败——这些在单体里根本不存在。

### 4. 技术栈异构

不同服务可以选用最合适的技术。用户服务用 Java,数据分析服务用 Python,各自选数据库。

**但这条要谨慎用**。技术栈异构的收益是"用对工具",代价是:

- 运维要维护多套环境
- 团队要掌握多种技术
- 跨语言的问题排查更难
- 通用组件(监控、日志、链路追踪)要支持多语言

**多数团队的实际情况是:保持统一技术栈,只在确实需要的服务上引入异构。** 为了"技术自由"而拆出一堆语言,通常得不偿失。

### 5. 去中心化数据管理

每个微服务拥有自己独立的数据库,**不共享数据库**。

这是微服务里最容易被违反、也最不该违反的一条。

```
❌ 错误:订单服务和用户服务共用一个库
   → 订单服务可以直接 JOIN 用户表
   → 两个服务的表结构强耦合,谁都不敢改
   → 数据库成为性能瓶颈和单点

✅ 正确:各自独立库
   → 订单服务要用户信息,通过接口拿
   → 表结构可以各自演进
   → 但要处理"跨服务查询"和"数据一致性"
```

**不共享数据库是微服务独立演进的前提**。一旦共享,两个服务就被数据库绑在一起了,拆分的意义消失大半。

代价是:原本一个 JOIN 能解决的问题,现在要拆成多次调用,或者做数据冗余。

### 6. 完善的配套基础设施

微服务需要一整套基础设施支撑:

| 组件 | 解决的问题 |
|---|---|
| 注册中心 | 服务地址动态变化,怎么找到对方 |
| 配置中心 | 配置统一管理、动态刷新 |
| API 网关 | 统一入口、鉴权、限流 |
| 熔断降级 | 一个服务挂了不拖垮全链路 |
| 链路追踪 | 一次请求跨多个服务,怎么排查 |
| 分布式事务 | 跨服务的数据一致性 |
| 集中日志 | 日志散在各处,怎么聚合 |
| 监控告警 | 几十个服务的健康状态怎么看 |

**这套基础设施不是可选项,是必需品。** 没有注册中心就无法做动态扩缩容,没有链路追踪就无法排查问题——而这些组件的搭建和维护本身就是可观的工作量。

### 7. 故障隔离

单个服务故障,理论上不会造成整个系统瘫痪;通过熔断限流阻止故障扩散。

**注意"理论上"三个字**。实践中,如果调用链很深且没有熔断,一个底层服务的延迟会沿着调用链一路放大——这就是**雪崩效应**:

```
服务 D 变慢(比如从 50ms 变 2s)
   ↓
服务 C 等 D,线程池被占满
   ↓
服务 B 等 C,线程池被占满
   ↓
服务 A 等 B,线程池被占满
   ↓
整个系统不可用
```

**故障隔离不是自动获得的,要靠熔断、超时、舱壁隔离这些机制主动实现。**

## 三、单体架构的痛点:微服务到底在解决什么

项目初期,单体架构往往是最好的选择——开发简单、部署简单、调试简单、没有分布式问题。

但随着业务变大,痛点是逐步累积的:

| # | 痛点 | 具体表现 |
|---|---|---|
| 1 | 代码膨胀 | 多人开发冲突严重,改一小块就要全量发布 |
| 2 | 数据库压力 | 所有功能共用一个库,单库成为瓶颈 |
| 3 | 故障扩散 | 一处 bug(比如某个接口内存泄漏)整个系统挂掉 |
| 4 | 无法针对性扩容 | 想扩订单模块,只能把整个应用多部署几份 |
| 5 | 迭代变慢 | 上线风险高,每次发布都要全员待命 |

### 痛点 4 值得展开

这是最容易被忽略但影响最直接的一条。

假设一个电商系统里,"商品浏览"占 90% 的流量,"订单"占 5%。单体架构下想扛住流量,只能**整个应用部署 10 份**——其中 9.5 份的算力浪费在订单模块上。

微服务下,商品服务部署 10 个实例,订单服务部署 2 个,资源利用率完全不同。

**这就是"独立扩容"的价值:让每个服务按自己的压力水平配置资源。**

## 四、微服务的代价

前面说了收益,这里必须把代价说清楚——**这些代价是真实的,而且往往被低估**。

| 代价 | 说明 |
|---|---|
| **运维复杂度上升** | 从"部署 1 个应用"变成"部署 N 个服务 + 一整套中间件" |
| **网络开销** | 本地调用变网络调用,延迟增加、序列化有成本 |
| **分布式新问题** | 分布式事务、数据一致性、分布式锁、定时任务重复执行 |
| **排查难度增加** | 一个请求跨多个服务,没有链路追踪几乎无法定位问题 |
| **测试复杂** | 集成测试需要拉起多个服务,或用 mock 替代 |
| **团队要求提高** | 每个开发都要理解分布式的基本问题 |
| **一致性变难** | 单体一个事务搞定的事,微服务要引入最终一致、补偿、对账 |

### 最容易被低估的:一致性

单体里,一个 `@Transactional` 就能保证"扣库存 + 创建订单"的原子性。

微服务里,这两个操作在不同的服务、不同的数据库,要引入分布式事务(Seata 等)、消息队列、补偿逻辑、对账兜底——**而且通常做不到强一致,只能做到最终一致**。

**业务能不能接受最终一致,是拆分前必须先确认的事。**

## 五、拆分的正确姿势

### 不该一开始就微服务

**推荐路径是"单体优先,必要时拆"**:

```
阶段 1: 单体应用,快速验证业务
   ↓ 业务增长、团队扩大、遇到明确痛点
阶段 2: 模块化单体(代码分层清晰,但还部署在一起)
   ↓ 痛点无法通过代码结构解决
阶段 3: 按业务域拆出少量核心服务(通常先拆最痛的)
   ↓ 基础设施完善,团队适应
阶段 4: 持续演进
```

**"模块化单体"是常被忽略的中间态**:代码上按业务域清晰分层、边界明确,但部署仍在一起。它保留了单体的部署简单,又把代码结构理顺了——**如果后续要拆,这种结构拆起来容易得多**。

### 拆分优先级

如果要开始拆,先拆哪些?

| 优先拆 | 理由 |
|---|---|
| 流量差异大的模块 | 独立扩容收益最直接 |
| 变更频繁的模块 | 减少全量发布 |
| 团队归属清晰的模块 | 边界明确,好落地 |
| 技术栈需求特殊的模块 | 比如需要 GPU 的 AI 模块 |

| 后拆 / 不拆 | 理由 |
|---|---|
| 强事务关联的模块 | 拆了要引入分布式事务,不划算 |
| 变更很少的模块 | 拆分收益低 |
| 数据强耦合的模块 | 拆了要处理大量跨服务查询 |

## 小结

- 微服务解决的是**组织与演进问题**,不是技术先进性——5 人团队不需要它
- 七个特点:单一职责、独立部署、网络通信、技术异构、**独立数据库**、**配套基础设施**、故障隔离
- 关键约束:**不共享数据库**是独立演进的前提;共享了,拆分就失去意义
- 单体的核心痛点:代码膨胀、数据库瓶颈、故障扩散、**无法针对性扩容**、迭代变慢
- 代价真实且容易被低估:**运维复杂度**、**网络开销**、**分布式新问题**、**排查难度**、**一致性变难**
- 最该确认的前提:**业务能否接受最终一致**
- 推荐路径:**单体 → 模块化单体 → 按业务域拆分**,不要一步到位
- 拆分优先级:流量差异大、变更频繁、团队归属清晰的模块先拆;**强事务关联的模块不拆**

架构选型没有"更先进",只有"更合适"。**能在单体里解决的问题,不要用微服务解决**——这是最省钱、最省心的判断。
